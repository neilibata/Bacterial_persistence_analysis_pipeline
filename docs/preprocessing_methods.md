## S.1 Overview

```
SRA / ENA accessions
   │  per sample: all runs retrieved, paired-end runs concatenated
   ▼
raw FASTQ ─► Trim Galore ─► bowtie2 vs PhiX ─► bowtie2 vs hg38
                                                     │
                                                     ▼
                                           BBTools repair.sh
                                                     │
                                                     ▼
                           bowtie2 --very-sensitive-local vs SGB catalogue
                                                     │
                                                     ▼
                                     samtools view -q 30  (high / low split)
                                                     │
                                                     ▼
                                         samtools coverage (per contig)
                                                     │
                                                     ▼
                           length-weighted aggregation to species (SGB)
                                                     │
                                                     ▼
                               depth and breadth matrices (samples × SGBs)
```

Implemented as a Snakemake workflow, one job per sample per stage, so a failure
at any stage affects only that sample and retries independently.

**Scale.** ~18,000 samples and **102.5 Tbp** of sequence, each aligned
independently against four reference catalogues (3,971, 3,594, 5,081 and 1,682
SGBs). This is the dominant computational cost of the study.

## S.2 Sample identity and run retrieval

The analytic unit is the biological sample, identified by `Chosen_match_ID`. It
does not correspond one-to-one with an archive run: **2,922 of 18,000 classified
samples (16.2%) were sequenced across multiple runs**, up to 35 for one sample.

All runs belonging to a sample are retrieved and **concatenated before
trimming**, in fixed order, identically for both mates. Aligning runs separately
would give one matrix row per run rather than per sample, and the two cannot be
reconciled afterwards: breadth is a percentage of genome covered, so per-run
breadth values cannot be pooled without the underlying alignments.

Runs are taken from the `Paired SRR List` field of Metadata Table M1, which is a
superset of `SRA_Accession` — **2,653 samples list runs the latter omits**.

**Single-end runs are excluded.** The pipeline requires paired-end data
throughout. A run's layout is read from the ENA `library_layout` field rather
than inferred from which output files appear, and excluded runs are recorded per
sample in `results/qc/<sample>.skipped_runs.tsv`. A sample with no paired-end run
fails rather than being silently emptied.

> **Archive note.** ENA and SRA do not always render the same run identically.
> SRA stores a re-encoded "Normalized Format"; for some runs the second mate is
> stored zero-length, so `fasterq-dump` reconstructs the run as single-end even
> where ENA holds it as paired. `ERR1913111` is the clear case: 16,534,250 reads
> in two files at ENA, single-end through SRA. Retrieval therefore defaults to
> SRA — matching how the bulk of the cohort was processed — and falls back to ENA
> for runs SRA cannot deliver as pairs, with downloads verified against ENA's
> published md5.

## S.3 Stage parameters

| Stage | Tool | Invocation | Rationale |
| --- | --- | --- | --- |
| Trim | Trim Galore | `--paired` | Adapter and quality trimming at defaults; both mates or neither |
| PhiX removal | bowtie2 | `--un-conc-gz --no-unal` | Sequencing spike-in; unaligned pairs retained |
| Host removal | bowtie2 vs hg38 | `--un-conc-gz --no-unal` | Human read depletion |
| Re-pair | BBTools `repair.sh` | `qin=33` | Decontamination can orphan mates; restores strict pairing |
| Align | bowtie2 | `--very-sensitive-local` | Sensitivity matters: the inferential target is the low-abundance tail |
| MAPQ filter | samtools | `view -b -q 30 -U <low>` | Single pass; both tiers retained so the discarded fraction is auditable |
| Coverage | samtools | `coverage` | Per-contig depth and breadth |
| Aggregate | `aggregate_coverage.py` | contig-length weighting | Contig → species |

`--very-sensitive-local` is the consequential choice. Reference-based alignment
was used rather than de novo assembly because assembly preferentially recovers
abundant taxa and would inflate apparent absence in shallow samples — the exact
quantity under study.

### Adapter and quality trimming

Trimming retained a **median 99.1% of bases per sample (IQR 95.4–99.5%;
n = 12,895 samples with surviving reports)**. Variation tracks study rather than
lifestyle group, reflecting differences in read length, base quality and adapter
content. Pre-trim base counts in the reports agree with the `Total bases` field
of Metadata Table M1 to a median ratio of 1.000 (n = 12,894), so sequencing input
volume is known for the full cohort. Regenerate with `tools/trim_coverage.py`.

### On MAPQ ≥ 30

Against catalogues of several thousand closely related genomes a large fraction
of read pairs align to more than one location and are discarded. **Of pairs
aligning concordantly, a median 67.4% (IQR 62.8–75.1%, range 57.0–89.9%) do so
at more than one location**, and are removed by the MAPQ filter.

This is deliberate: retaining ambiguous alignments would attribute reads to
species that may not be present, which for a study of taxon absence is the
costlier error. Reported depth is therefore a conservative lower bound, applied
identically across all samples and lifestyle groups.

The fraction is measured on the stratified 27-sample subset described in §S.7.4,
because per-sample alignment logs from the original staged execution survive only
in part. Regenerate with `tools/parse_preprocessing_logs.py`.

### Stage-by-stage attrition

Measured on the same 27-sample stratified subset:

| Stage | Retained (median) | IQR | Range |
| --- | ---: | ---: | ---: |
| Adapter/quality trimming | 99.45% of bases | 96.29–99.57% | 81.62–99.67% |
| PhiX removal | 100.00% of pairs | 100.00–100.00% | 99.89–100.00% |
| Host (hg38) removal | 100.00% of pairs | 99.98–100.00% | 71.21–100.00% |
| Overall alignment rate | 88.14% | 85.88–89.81% | 74.22–93.92% |

PhiX contamination is negligible (0.0098% of pairs discarded, pooled), consistent
with spike-in having been removed by most submitters before deposition. Human
read content is also low in aggregate (0.298% pooled) but strongly
sample-dependent: the most host-contaminated sample in the subset lost 28.8% of
its pairs at this stage, which is why the step is retained despite its small
average effect.

Cohort totals, sequenced bases versus bases mapped at MAPQ ≥ 30:

| --- | --- | ---: | ---: | ---: | ---: |
| Carter/UHGG | Hunter-gatherer | 7.8 Tbp | 2.5 Tbp | 32.1% | 6.08 ± 0.22 Gb |
| Carter/UHGG | Transitional | 34.4 Tbp | 10.6 Tbp | 30.8% | 3.07 ± 0.04 Gb |
| Carter/UHGG | Industrial | 60.3 Tbp | 23.4 Tbp | 38.8% | 1.64 ± 0.01 Gb |
| Leviatan | Hunter-gatherer | 7.8 Tbp | 2.3 Tbp | 29.5% | 5.75 ± 0.21 Gb |

| Leviatan | Industrial | 60.2 Tbp | 23.0 Tbp | 38.2% | 1.62 ± 0.01 Gb |
| Combined | Hunter-gatherer | 7.8 Tbp | 2.8 Tbp | 35.9% | 6.89 ± 0.24 Gb |

| Combined | Industrial | 60.3 Tbp | 27.7 Tbp | 45.9% | 1.94 ± 0.01 Gb |

Leviatan's sequenced totals now match Carter's to within rounding, where before
the backfill they were 7.7 / 30.5 / 59.7 Tbp — the 398 restored samples account
for 3.9 Tbp in the transitional group alone.

Industrial samples map 7–12 percentage points more of their sequence than
non-industrial samples, in every catalogue — including Carter/UHGG, the
catalogue enriched for non-industrial discovery. A greater share of
non-industrial sequence therefore has no reference representative at all.

**The direction of this asymmetry is conservative with respect to the central
claim.** Sequence that maps to nothing is diversity the method cannot count, so
measured non-industrial richness is a lower bound and the industrial versus
non-industrial difference is, if anything, understated. It is also the clearest
empirical motivation for analysing two catalogues with opposing discovery biases
rather than one.

## S.4 Aggregation to species level

`samtools coverage` reports per contig. Species-level values are contig-length
weighted means over all contigs assigned to that SGB:

- weighted mean depth = Σ(meandepth_c × L_c) / Σ L_c
- weighted mean breadth = Σ(coverage_c × L_c) / Σ L_c

with corresponding weighted standard deviations. **Contigs present in the
reference but absent from the coverage output are included as zeros**, so the
denominator is always the full species genome length and breadth is comparable
across species regardless of how many contigs were hit.

## S.5 Matrix assembly, the Leviatan backfill, and the combined reference

Each workflow run writes a **dated shard** (`depth_matrix_YYYYMMDD.csv`), merged
into the canonical matrix. Column order is fixed by the contig map, so shards are
column-identical and a backfill never rewrites samples already processed.
`verify_completeness.py` asserts that every requested sample reached the matrix
and exits non-zero otherwise.

### The Leviatan backfill

Reconciling Metadata Table M1 against each reference's matrix found **398
classified samples absent from Leviatan** and none from Carter/UHGG or combined.
They fell into two groups:

- **309 genuinely unprocessed**, concentrated in `BeghiniF` (306).
- **89 present only as run-level rows.** All are multi-run samples from
  `LiSS_2016_NLD` (55), `BedarfJR_2017_DEU` (26) and `LomanNJ_2013` (8). Carter
  and combined held them correctly as one row per sample; Leviatan held 336
  separate run rows. Because breadth cannot be pooled post hoc, these required
  reprocessing rather than remapping.

All 398 were reprocessed and merged (`tools/merge_lev_backfill.py`), taking the
Leviatan matrix from **23,914 to 24,312 rows**. Merging is by column name rather
than position: the shard and published matrix share a column set but not an
order, so a positional append would have silently misaligned all 3,594 species.

### The combined reference

The combined catalogue is **not a separate alignment**. 5,081 non-redundant
representatives were derived by sourmash sketching, symmetric containment ANI and
clustering at ≥95% (2,484 SGBs shared between catalogues); each representative
keeps the values from whichever source catalogue won the representative choice —
**2,883 from UHGG, 2,198 from Leviatan**. The combined matrix is therefore a
column-wise merge, and the clustering result is frozen in
`combined_sgb_metadata.xlsx`.

The original construction took the **union** of samples, so a sample present in
UHGG but absent from Leviatan was carried in with all 2,198 Leviatan-derived
columns set to zero — indistinguishable from genuinely absent taxa, and
systematically depressing that sample's richness across 43% of the catalogue.
**421 matrix rows were affected**, of which 398 were classified cohort samples.

`tools/build_combined_matrix.py` rebuilds on the **intersection**: a sample
lacking data in either source is excluded and counted, never zero-filled. After
the backfill the intersection rises from 23,515 to **23,913** and the excluded
count falls from 421 to **23** (orphan rows with no metadata entry).

## S.6 How the cohort was actually processed

**Original execution.** At this scale the preprocessing was carried out **in
stages over an extended period**, orchestrated by hand: batches of samples were
submitted, checked for completion, and the next stage launched once the previous
had finished. Per-sample logs from that execution survive only in part.

**The deposited workflow is a faithful reimplementation of those same steps.**
Tools, parameters, order of operations and thresholds are identical; what the
Snakemake implementation adds is orchestration, per-run provenance capture,
explicit completeness verification and dated output shards. It is a
reproducibility and auditability improvement, not a methodological change.

**Reproduction scope.** The deposited pipeline regenerates the matrices from raw
accessions and has been run end to end on subsets. The full cohort has not been
re-executed in a single pass, which would take approximately a month of cluster
time; the results presented here come from the staged execution above. Equivalence
was therefore measured directly (§S.7.4) rather than assumed.

**Version provenance.** The workflow is tagged `v1.0-as-published`, preserved
unchanged, with later tags fixing defects found during pre-submission audit.
`results/provenance/` records the exact version of every tool, per run.

## S.7 Quality control and validation

Each check below states what could go wrong, what was measured, and the command
that regenerates it. Several were added because an earlier defect had been
invisible to presence-based checks — a sample can be *present but empty*, and
that distinction accounts for most of what follows.

### S.7.1 Cohort completeness and identity

| Check | Result |
| --- | --- |
| M1 samples absent from each matrix | UHGG 0, combined 0, Leviatan 398 → **0 after backfill** |
| Leviatan `cohort_matched_to_matrix` | 17,650 → **18,299** (full metadata cohort) |
| Duplicate `Chosen_match_ID` in M1 | 21, resolved deterministically by largest `Total bases` |
| Run accessions shared between samples | **0** |
| Duplicate BioSample / SRA_Accession / Secondary_run_IDs | **0 / 0 / 0** |
| Exact duplicate rows in the merged matrix | **0** (24,312 rows, 24,312 unique IDs) |
| Backfilled samples clashing with existing rows | **0** |

Identifier uniqueness matters because the cohort is assembled from 83 studies;
the same specimen deposited twice would be pseudo-replication. No two samples
share sequencing data. Regenerate with `tools/reconcile_cohorts.py`.

Metadata base accounting is internally consistent: `number_reads ×
median_read_length / Total bases` has median **1.000** (IQR 1.000–1.007) across
all 18,000 samples.

### S.7.2 Reference integrity

A reference artefact can be wrong at one level while looking correct at another,
and the failure only surfaces far downstream. Three checks close that gap.

| Check | Result |
| --- | --- |
| Contig map species column is species-level, not contig-level | enforced at parse time by `validate_contig_map()` |
| Distinct species per catalogue | UHGG **3,971**, Leviatan **3,594**, combined **5,081** |
| Lengths file matches matrix columns | **3,971 / 3,594 / 5,081**, exact, zero either-side |
| SGB lengths agree across reference lengths files | **0 differences** (2,883 UHGG↔combined, 2,198 Leviatan↔combined) |
| bowtie2 index contig names ∩ contig map | verified before each run |

The lengths check matters because breadth and depth are length-weighted; a
disagreement between the lengths a matrix was built with and the lengths the
analysis normalises by would distort every mean silently. There are none.

A contig map whose species column carries contig identifiers parses without error
and yields one matrix column per contig — 251,424 instead of 3,971 in an instance
we encountered. `validate_contig_map()` now refuses any map whose species column
has more than half as many distinct values as its contig column.

### S.7.3 Matrix integrity

Run on the 398-sample backfill shard, the only new data (1,430,412 cells):

| Check | Result |
| --- | --- |
| depth > 0 with breadth = 0 | **0** |
| depth = 0 with breadth > 0 | **0** |
| breadth outside [0, 100] | **0** (observed range 0.0000–99.5190) |
| depth < 0 | **0** (observed range 0–1950.12) |
| NaN or infinite values (4 matrices) | **0** |
| Sample and column order identical between depth and breadth | ✅ |
| All-zero backfilled samples | **0 of 398** |

Mutual consistency between depth and breadth is the check that would catch a
mis-paired column block: the two matrices are built from the same aggregation, so
a species with coverage must have depth and vice versa.

The merged Leviatan matrix contains 209 all-zero rows, **198 of which have no
Metadata M1 entry** (orphan run-level rows, filtered on load). The remaining 11
are classified samples that produced no signal against **either** catalogue; they
fall below the ≥30 Mb mapped-bases threshold and are excluded at load, and are
listed in Table S2b.

Published matrices were checksummed (SHA-256) before any modification and
re-verified afterwards: **all six unchanged**. The backfill and rebuild write new
versioned files and never modify published ones in place.

### S.7.4 Concordance: does the deposited code reproduce the original?

Because the full cohort could not be re-executed, equivalence was measured on a
subset. **27 samples** were drawn by a seeded, stratified sample across all three
lifestyle groups and three sequencing-depth terciles
(`tools/concordance_check.py select`), reprocessed from raw accessions through
the deposited workflow, and compared against their rows in the published matrix.

| Result | |
| --- | --- |
| Samples reproducing exactly | **25 of 27** |
| Per-sample Pearson r (median) | **1.000000** |
| Total mapped bases, agreement | within **1.4 × 10⁻⁵** |
| Detection difference | −6 to +6 SGBs of ~5,000 |

Two samples differed, both recovering **more** sequence than the original:

- **`SRR061226` (×1.96 bases, +458 SGBs)** — has two runs in `Paired SRR List`
  and none in `SRA_Accession`; the original processing used one. The rerun is
  more complete.
- **`ERR7746144` (×1.52 bases, +165 SGBs)** — a single run in both lists;
  the cause could not be determined.

In both cases the discrepancy raises rather than lowers recovered signal, so the
published matrices under-count for affected samples and no result is inflated.
That the test detected a difference at all is itself informative: a uniform 27/27
would have been weaker evidence.

### S.7.5 Mapping rate varies by study, not by processing

Mapped bases as a fraction of sequencing input were computed for every sample
against every catalogue (`tools/mapped_fraction_outliers.py`). Flagging samples
more than three robust standard deviations below their own study's median
identifies 328 samples across all three references — but these are **not**
processing failures. They concentrate in a small number of studies, `MehtaRS_2018`
alone contributing 129, and that is the study with the lowest trimming retention
in the cohort (82.5% of bases, against a cohort median of 99.1%). Low mapping
there is a property of the deposited data — read length, base quality and adapter
content — rather than of how it was processed.

This is worth stating because it bears on interpretation: **between-study
variation in mapping rate is larger than any within-study variation attributable
to processing.** It is also why the read-volume accounting above is reported per
lifestyle group rather than per study, and why the ≥30 Mb mapped-bases inclusion
threshold is applied on mapped rather than sequenced bases — the latter would
admit samples whose sequence does not reach the reference at all.

### S.7.6 Multi-run samples: a bounded, one-directional shortfall

The concordance test (§S.7.4) found `SRR061226` had been processed from one of
its two sequencing runs, recovering 1.96× more sequence on reprocessing. Because
that sample reached the subset by chance, the cohort was screened for the same
signature.

A generic "unusually low mapping" rule does not work: mapping rate varies far
more between studies than within them (§S.7.5), and such a rule misses
`SRR061226` entirely, since half-normal mapping sits inside ordinary study
spread. Partial processing instead leaves a specific arithmetic trace — a sample
with *N* runs of which *k* were used maps roughly *k/N* of what comparable
samples in the same study achieve. Testing multi-run samples against
single-run samples in the same study for such sub-multiples
(`tools/mapped_fraction_outliers.py --multirun`) recovers `SRR061226` correctly
at a ratio of 0.532, matched as 1/2.

**106 of 18,000 samples (0.6%)** show this signature, concentrated in
`HMP_2012_USA` (48), `USA_2012_HMP` (18) — the same cohort under two labels —
and `ZeeviD_2015_ISR` (19). The commonest ratio is 1/2 (59 samples), with 15 at
1/8.

Two explanations produce an identical signature, and we cannot presently
separate them: the runs were available and not all were used, or `Total bases`
in the metadata sums runs for which no sequence was ever retrievable. ENA lists
base counts for the unused runs but serves no FASTQ for them; that does not
settle it, because retrieval uses SRA rather than ENA FTP, and `SRR061226`'s
second run was demonstrably obtainable that way.

Three things bound the consequence:

1. **One case is confirmed**, the remaining 105 are candidates.
2. **The direction is under-counting.** Affected samples have less sequence
   attributed to them than they should, never more, so no richness estimate is
   inflated.
3. **The affected samples are overwhelmingly industrial** (HMP and ZeeviD), the
   group whose richness the central claim reports as *lower*. Correcting them
   would therefore act against the reported effect, not for it.

Candidates are written to `results/qc/mapped_fraction_outliers.csv` by
`python tools/mapped_fraction_outliers.py`, which is standalone rather than part of
`python -m persistence`, so the file is absent until that is run. Reprocessing the
candidates is straightforward with the deposited workflow and is deferred rather than
undertaken here.

### S.7.7 Checks pending

The Leviatan and combined analyses these were waiting on have since run, so the first
is answered and the rest remain open:

> 1. **Taxon-list stability — answered.** VANISH+/BloSSUM+ are data-derived (the
>    100 most differentially prevalent taxa per list), and membership does move:
>    membership shifts with the cohort. Metadata Table M3 (Data S4) therefore
>    describes the lists the reported run derived. The quantities that do not
>    depend on exact membership — catalogue sizes, pooled detection counts,
>    median N-to-detect — reproduce exactly, so the movement is confined to the
>    100-taxon cut rather than the underlying signal.
> 2. **Mapped-fraction outliers.** `total_bp / Total bases` per sample per
>    reference, flagging the low tail — the systematic form of the `SRR061226`
>    defect, which the 27-sample draw caught only by chance.
> 3. **Cross-study specimen duplication.** Whether two distinct BioSamples are
>    the same specimen deposited by related consortia, suspected for the
>    MetaHIT-derived Danish studies. Metadata shows 1,023 samples with 1,023
>    distinct BioSamples and no shared runs, so only sequence similarity can
>    answer it.
> 4. **Reinstatement determinism.** Confirming the Bray-Curtis replicate screen
>    is not order-dependent.

## S.8 Reproducing it

```bash
git clone https://github.com/neilibata/Bacterial_persistence_preprocessing
cd Bacterial_persistence_preprocessing && bash setup.sh
# edit config/config.yaml: sample list, reference FASTA, contig map
snakemake --profile profiles/slurm
```

Inputs required: a sample list (one accession per line, or
`sample_id <TAB> run1;run2` for multi-run samples), the reference FASTA, and the
contig→species map. Host, PhiX and all bowtie2 indices are built automatically.

Validation commands used above:

```bash
python tools/reconcile_cohorts.py            # cohort completeness, identity
python tools/trim_coverage.py                # trimming retention and log coverage
python tools/parse_preprocessing_logs.py     # read-volume cascade, multi-mapping
python tools/concordance_check.py select     # stratified reproduction subset
python tools/concordance_check.py compare    # equivalence against published
python tools/build_combined_matrix.py --validate
python tools/merge_lev_backfill.py
python tools/verify_reproducibility.py
```
